================================================================================
EXECUTIVE SUMMARY
================================================================================
This report provides an accurate, verifiable evaluation of the current Cyber
Security Club MRDU portal codebase. Critical vulnerabilities relating to hard-
coded credentials and unverified fallbacks have been remediated. Production
startup now strictly enforces required environment secrets and refuses to run
with insecure defaults. Role-based access control, CSRF protection, and AES-256-
GCM encrypted database sessions are enforced server-side.

================================================================================
1. REMEDIATED VULNERABILITIES
================================================================================
1.1 Hard-coded Credentials in Source & Scripts                    [REMEDIATED]
    - Status: REMEDIATED.
    - All hard-coded passwords and secrets have been removed from source code,
      bootstrap scripts, deployment guides, and tracked files.
    - President initial provisioning requires explicit PRESIDENT_INITIAL_PASSWORD
      via environment variables.

1.2 Hard-coded Production Session Secret Fallbacks                [REMEDIATED]
    - Status: REMEDIATED.
    - Fallback defaults for SESSION_SECRET and SESSION_ENCRYPTION_KEY in production
      have been removed. In production (NODE_ENV=production), the application
      refuses to start if secrets are missing.
    - Development mode generates ephemeral in-memory keys for local workflows.

1.3 Cross-Site Request Forgery (CSRF) Protection                  [REMEDIATED]
    - Status: REMEDIATED.
    - Stateful mutation endpoints require an HMAC-signed X-CSRF-Token header.
    - Tokens are bound to the user session.

1.4 Inadequate Session Storage & Plaintext State                  [REMEDIATED]
    - Status: REMEDIATED.
    - Session records in MySQL/MariaDB are encrypted at rest using AES-256-GCM.
    - Cookies are HTTP-only, SameSite=Lax/Strict, rolling, with secure flags.

1.5 Multi-Factor Authentication (TOTP) Safeguards                 [REMEDIATED]
    - Status: REMEDIATED.
    - TOTP secrets are encrypted at rest using AES-256-GCM.
    - Sensitive operations such as Primary President role transfer require 2FA
      verification.

1.6 Primary President Account Protection                          [REMEDIATED]
    - Status: REMEDIATED.
    - The Primary President account cannot be deleted by any administrator.
    - Primary President status can only be transferred by the authenticated
      Primary President.

1.7 Content Security Policy & Frame Embedding                     [REMEDIATED]
    - Status: REMEDIATED.
    - Helmet CSP strictly restricts scripts, objects, connections, and frame
      sources, allowing only self and official YouTube embed domains
      (https://www.youtube.com and https://www.youtube-nocookie.com).

================================================================================
2. ACCEPTED BEHAVIOR / OUT OF SCOPE
================================================================================
The following architectural choices are accepted by design:
- Single-instance in-memory rate limiting for initial college deployment scale.
- Client-rendered inline styles (style-src 'unsafe-inline') for dynamic theme
  and layout elements, mitigated by strict script-src and object-src restrictions.
- Event capacity and image URL validations are handled at application business
  logic layers.

================================================================================
3. SECURITY HARDENING RECOMMENDATIONS
================================================================================
3.1 Distributed Rate Limiting (Redis)                             [RECOMMENDED]
    - For multi-instance load-balanced production scaling, transition Express
      rate limiters from MemoryStore to Redis.

3.2 Off-site Encrypted Database Backups                           [RECOMMENDED]
    - Implement automated daily snapshots and encrypted backups of the MySQL
      database on Railway or cloud object storage.

3.3 Email Ownership Verification for Password Reset               [RECOMMENDED]
    - Ensure SMTP credentials are provided in production so email verification
      and password recovery emails can be delivered securely.
